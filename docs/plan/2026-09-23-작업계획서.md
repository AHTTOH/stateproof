**핵심 판단 세 가지.**

1. **범위는 "정책 1개 · 크리덴셜 2종 · 연산자 6개" 로 자른다.** PRD 의 API/SDK·웹훅·과금·팀 관리·Enterprise 항목은 전부 제외한다. 심사 기준이 "클론해서 컴파일되고, README 대로 데모가 돌아가는가" 이므로 **동작하는 좁은 범위**가 넓은 미완성보다 낫다.
2. **네트워크 호환 버전에 고정한다.** Compact 컴파일러 0.31.1 · compact-runtime 0.16.0 · Midnight.js 4.1.1 · Proof Server 8.1.0 · DApp Connector 4.0.1 (호환 매트릭스 2026-09-22 기준). 최신 컴파일러 0.34.0 은 ledger 9 대상이라 **Preprod 에 배포가 안 된다.** 이걸 놓친 참가 프로젝트(VeriShield)가 실제로 Preprod 배포 실패 상태다.
3. **환경은 "전부 외부" 로 간다 (2026-09-25 갱신).** Midnight 재단이 Preprod 공용 Proof Server(`https://proof-server.preprod.midnight.network`, 8.1.0)를 운영 중인 것을 실측으로 확인했다. 따라서 Docker 는 어디에도 필요 없고, 웹 UI 는 Firebase Hosting 또는 Vercel 에 올리며, 남는 리눅스 의존은 Compact 컴파일러 하나다. 컴파일러를 Hermes 사용자 공간에 둘지 GitHub Codespaces 에 둘지만 정하면 된다(§10 결정 1). 로컬 PC 에는 아무것도 설치하지 않는다.

## 3. PRD 를 해커톤 범위로 축소

PRD 는 SaaS 전체(3주체 + 콘솔 + API/SDK + 과금)를 그린다. 5일 안에 "동작하는 것"으로 만들 수 있는 것은 아래 MVP 열이다. 나머지는 README 의 로드맵 절에 PRD 그대로 옮겨 적어 "제품 비전 vs 해커톤 구현" 을 분리해 보여준다.

| PRD 절 | 항목 | MVP (D0~D4) | 해커톤 제외 |
|---|---|---|---|
| §5 Dynamic Policy Builder | 연산자 | 숫자 `>=`, `<=`, `=`, `≠`, `Between`, 범주 `In` (6개) · 조건 최대 4개 · AND | OR 조합, `Not In`, 날짜 전용 연산자(숫자로 환산해 처리), Before/After |
| §9 Credential | 스키마 | EmploymentCredential, IdentityCredential (2종) | IncomeCredential, Education, License, 외부 포맷 Adapter |
| §10 Credential Wallet | 홀더 지갑 | 브라우저 private state 에 크리덴셜 보관·목록·발급기관·만료 표시 | raw value 열람 UI, 여러 지갑 동기화 |
| §4·§6 Verification Request | 요청 | Verification Link (URL 에 requestId) | QR, API Request, SDK |
| §7 검증 결과 | 결과 | 온체인 VERIFIED 기록 + Verifier 콘솔에 표시 | 결과 유효기간 만료 처리 UI |
| §8 Selective Disclosure | 부분 공개 | Should: 정책에 공개 마스크 1개 필드 | 다중 필드·동의 UI 세분화 |
| §11 Verifier Console | 콘솔 | 정책 저장(브라우저)·요청 목록·상태(Pending/Verified/Expired) | Rejected 상태, Analytics, 팀 관리 |
| §12 API / SDK | 외부 연동 | 제외 | 전부 |
| §13 Midnight 역할 | ZK | Compact 회로에서 서명 검증 + 술어 평가 + 온체인 결과 기록 | 크로스 컨트랙트 |
| §14 Generic Proof Engine | 엔진 | **단일 회로 `submitProof` 가 정책을 public 입력으로 받아 평가** (핵심 차별점) | 스키마 동적 추가 |
| §17 Verification Receipt | 영수증 | 온체인 결과 레코드의 해시를 영수증 ID 로 사용, 링크로 공유 | QR |
| §19 비즈니스 모델 | 과금 | 제외 | 전부 |
| §20 Issuer | 발급 | 키 생성·서명·발급(CLI + 최소 UI), 만료 필드 | 취소(Revocation) 는 Could |

**MVP 데모 시나리오 (심사자가 따라할 한 줄기).**
Verifier 가 "재직 상태 = Active AND 근속 ≥ 12개월 AND 거주지 ∈ {서울, 경기}" 정책으로 요청 링크를 만든다 → Holder 가 링크를 열어 "무엇을 증명하고 무엇은 넘어가지 않는지" 화면을 보고 [Verify privately] 를 누른다 → 브라우저가 로컬 Proof Server 로 ZK 증명을 만들고 Lace 로 트랜잭션을 보낸다 → Verifier 콘솔에 VERIFIED 와 영수증이 뜬다. 원본 생년월일·정확한 근속·주소는 어디에도 남지 않는다.

**환경 선택지 (§10 결정 1). 2026-09-25 갱신.**

2026-09-25 실측으로 전제가 바뀌었다. **Midnight 재단이 Preprod 용 공용 Proof Server 를 운영 중이다.** `https://proof-server.preprod.midnight.network` 가 버전 8.1.0(호환 매트릭스와 일치)으로 응답하고, `/health` 정상, 브라우저 교차 출처(CORS) 요청도 허용한다(임의 Origin 으로 preflight 성공). Preview 용 `proof-server.preview.midnight.network`(8.0.3)도 있다. 즉 **증명 생성을 위해 Docker 를 어디에도 설치할 필요가 없다.** 남는 리눅스 의존은 Compact 컴파일러 하나뿐이다.

- **D. 전부 외부 (추천).** 웹 UI 는 Firebase Hosting 또는 Vercel 에 정적 배포. 증명은 공용 Proof Server URL 을 `config/networks.json` 에 두고 DApp 의 `proofProvider` 가 그 URL 을 쓴다. 컴파일러만 리눅스 셸 하나가 필요한데 후보는 두 가지다. **D-1 Hermes 사용자 공간**(nvm+Node 24, pnpm, compact CLI. Docker·sudo·재부팅 없음, 약 10분, 실서버 변경이므로 동의 필요) 또는 **D-2 GitHub Codespaces**(gh 에 `codespace` 스코프 추가 인증 1회 필요, 무료 한도 월 120 코어시간, 2코어 8GB 기본). 로컬 PC 에는 아무것도 설치하지 않는다. 주의: 공용 서버로 홀더의 크리덴셜 witness 가 전송된다. 테스트넷 가공 데이터라 감수하되 README 한계 절과 화면 배너에 명시한다.
- **A. Hermes 에 Proof Server 까지 자체 운영.** D 의 백업. 공용 서버가 느리거나 죽으면 `docker run -p 6300:6300 midnightntwrk/proof-server:8.1.0` 한 줄로 전환하고 cloudflared 로 HTTPS 를 붙인다. Hermes 는 "빈약한 무료 서버" 가 아니다. 4코어·24GB 로 로컬 노트북(13.7GB)보다 메모리가 크고, 증명은 CPU 보다 메모리가 관건이다.
- **B. 로컬 WSL2.** 더 이상 권하지 않는다. 관리자 권한·재부팅·Docker Desktop 이 필요하고 남은 3일 중 반나절을 소모한다.
- **Lace 지갑 주의.** 공식 문서는 "Lace 안에서는 로컬 Proof Server 만 지원" 이라 적혀 있으나, 2026-04 설치 가이드들은 지갑 생성 시 "Remote" 선택지를 언급한다. 공용 서버가 실재하므로 Remote 가 그것일 가능성이 높다. 09-25 Lace 설치 직후 확인하고, Remote 가 없으면 심사자용 README 에 "로컬 proof server 1줄 실행" 을 대안으로 적는다. DApp 쪽 증명은 Lace 와 무관하게 공용 서버로 간다.

### 4.4 서명·해시 실현 가능성 (compact-runtime 0.16.0 패키지 직접 확인)

`@midnight-ntwrk/compact-runtime@0.16.0` 의 `dist/*.d.ts` 에서 아래 TS 함수를 확인했다. 즉 회로 안에서 쓰는 것과 **동일한 해시·곡선 연산을 발급자가 TS 에서 그대로 실행**할 수 있다.

```
transientHash, persistentHash, persistentCommit, transientCommit,
ecMulGenerator, ecMul, ecAdd, hashToCurve, jubjubPointX, jubjubPointY,
degradeToTransient, upgradeFromTransient
```

`jubjubSchnorrVerify` 는 0.16.0 런타임에 없다(0.34 계열 stdlib 에 추가된 것으로 보임). 따라서 Schnorr 검증은 credential-compact 가 0.31.1 에서 한 방식 그대로 **직접 작성**한다: `ecMulGenerator(s) == R + ecMul(pk, c)`, `c = transientHash(bodyRoot ‖ pk ‖ R)`.

## 5. 아키텍처 설계

### 5.1 주체와 흐름

```
Issuer (TS, 오프체인)                Holder (브라우저)                     Verifier (브라우저)
  키 생성 sk/pk                                                            정책 작성 (UI)
  pk 를 온체인 등록 ──────────► [Contract] trustedIssuers                   createRequest(tx) ──► [Contract] requests
  credential 서명 (pure circuit                                                                   (policy 는 public 파라미터)
   sign 을 runtime 으로 실행)
  credential JSON 전달 ──────► private state 저장
                                 링크 열기 → 요청 내용 확인
                                 [Verify privately]
                                   witness: credential, signature, holderSecret
                                   Proof Server(로컬 6300) → ZK proof
                                   Lace → submitProof(tx) ─────────────────► [Contract] results[requestId] = VERIFIED
                                                                             Verifier 콘솔이 indexer 로 읽어 표시 + 영수증
```

Midnight 가 하는 일: **정책 = public 입력, 크리덴셜 = witness(private)**. 회로가 (1) 발급자 서명 검증 (2) 만료 검증 (3) 홀더 바인딩 (4) 술어 평가를 모두 증명 안에서 수행하고, 온체인에는 requestId 와 결과만 남는다. PRD §13 그림과 1:1 대응.

### 5.2 크리덴셜 데이터 모델 (Compact 측)

```
struct Credential {
  schemaId:     Bytes<32>            // 스키마 레지스트리(core) 의 ID 해시
  issuerId:     Bytes<32>
  holderCommit: Bytes<32>            // persistentHash(holderSecret)
  claims:       Vector<8, Uint<64>>  // 슬롯 의미는 스키마가 정의 (아래)
  issuedAt:     Uint<64>             // unix seconds
  expiresAt:    Uint<64>
  salt:         Field
}
struct Signature { r: JubjubPoint, s: Field }
```

- 모든 클레임을 **`Uint<64>` 로 인코딩**한다. 날짜는 unix days, 범주(재직상태·직군·지역)는 스키마의 코드표, 문자열은 코드표 또는 해시 하위 비트. 이유: Compact 의 `<`, `>=` 는 Uint 에만 있고 Field 에는 없다.
- 클레임 8슬롯은 고정 상수 `CLAIM_SLOTS = 8`. 이 값과 조건 수 `MAX_CONDITIONS = 4` 는 Compact 모듈 한 곳과 core 의 `constants.ts` 한 곳에만 두고, 두 값이 같은지 테스트로 묶는다.
- 오프체인 표현은 W3C VC JSON 형태를 유지하고, core 의 인코더가 위 구조로 정규화한다(PRD §9 "Adapter 로 내부 스키마 정규화").
- 커밋(bodyRoot)은 **`transientHash<Credential>`** 사용. `persistentHash` 는 SHA-256 이라 회로 비용이 크다. "업그레이드 간 지속 미보장" 은 해커톤 범위에서 감수하고 README 한계 절에 적는다.

### 5.3 스키마 (MVP 2종)

| 스키마 | 슬롯 0 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|---|
| EmploymentCredential | employmentStatus (1=Active, 2=Leave, 3=Terminated) | jobCategory 코드 | employmentStartDate (days) | employmentMonths (발급 시점 계산) | 예비 |
| IdentityCredential | birthDate (days) | ageYears (발급 시점 계산) | nationality 코드 | regionCode (시·도) | 예비 |

스키마 정의는 `packages/core/src/schemas/*.json` 단일 출처. UI 의 Policy Builder 셀렉트 박스, 발급자 인코더, README 의 표가 전부 이 JSON 에서 생성된다. 코드에 슬롯 번호를 직접 써넣지 않는다.

### 5.4 정책과 Generic Predicate Engine (PRD §14 의 핵심 구현)

```
enum Op { none, gte, lte, eq, neq, between, inSet }
struct Condition { claimIndex: Uint<8>, op: Op, value: Uint<64>, value2: Uint<64>, set: Vector<4, Uint<64>> }
struct Policy    { schemaId: Bytes<32>, issuerId: Bytes<32>, conditions: Vector<4, Condition>, discloseIndex: Uint<8> }
```

- Compact 는 동적 인덱싱·동적 길이 루프가 없다. 그래서 `for i of 0..4`, `for j of 0..8` 고정 루프로 **모든 슬롯·모든 연산자를 계산한 뒤 선택(mux)** 한다. 연산자 집합이 유한하므로 회로는 하나로 고정되고, **정책 값은 컴파일 시점이 아니라 요청 생성 시점에 정해진다.** PRD §14 "Value 는 contract 코드에 고정하지 않는다 · 완전히 임의의 프로그램은 아니다" 를 그대로 만족한다.
- `op == none` 인 조건은 항상 참(빈 슬롯). AND 만 지원.
- `discloseIndex` 가 유효하면 해당 슬롯 값 하나를 `disclose()` 해 결과 레코드에 남긴다(Selective Disclosure, Should).

### 5.5 온체인 상태와 회로

| 구분 | 이름 | 내용 |
|---|---|---|
| ledger | `admin: Bytes<32>` | 배포자 `ownPublicKey()` 해시. 발급자 등록 권한 |
| ledger | `trustedIssuers: Map<Bytes<32>, IssuerRecord{pkX: Field, pkY: Field, active: Boolean}>` | 신뢰 발급기관 |
| ledger | `requests: Map<Bytes<32>, Request{policy, referenceTime: Uint<64>, expiresAt: Uint<64>, createdAt}>` | 검증 요청. 정책이 public 으로 기록됨 |
| ledger | `results: Map<Bytes<32>, Result{status: Uint<8>, verifiedAt, disclosedValue: Uint<64>, receipt: Bytes<32>}>` | 결과 + 영수증 해시 |
| circuit | `registerIssuer(issuerId, pk)` | admin 전용 |
| circuit | `createRequest(requestId, policy, referenceTime, expiresAt)` | Verifier 가 호출 |
| circuit | `submitProof(requestId)` | witness `credential()`, `signature()`, `holderSecret()`. 순서: 요청 존재·미만료 → 발급자 pk 조회 → 서명 검증 → `expiresAt > referenceTime` → `persistentHash(holderSecret) == holderCommit` → 술어 4개 평가 → 결과 기록 |
| pure circuit | `sign(sk, credential, nonce)` / `credentialRoot(credential)` / `verifySignature(pk, sig, c)` | 발급자가 TS 에서 증명 없이 실행. 홀더 증명에서 재사용 |

시간 기준 `referenceTime` 은 요청 생성 시 Verifier 가 넣는 public 값이다. Compact 0.31 회로 안에서 블록 시간을 읽을 수 없기 때문이며, README 한계 절에 명시한다.

### 5.6 오프체인 구성

| 패키지 | 역할 | 기술 |
|---|---|---|
| `contract` | Compact 소스, 컴파일 산출물(`managed/`), 시뮬레이터 단위 테스트 | Compact 0.31.1, compact-runtime 0.16.0, vitest |
| `core` | 스키마 레지스트리(JSON), 정책 타입·빌더, 클레임 인코더, 서명 래퍼, 영수증 생성, 상수 | TS, 브라우저·Node 공용 |
| `issuer` | 키 생성, 크리덴셜 발급 CLI, 데모용 발급 API 1개 | Node, core 사용 |
| `web` | 단일 React 앱, 라우트 `/verifier` `/holder` `/issuer` | Vite + React, Lace(DApp Connector 4.0.1), Midnight.js 4.1.1 providers 6종. `proofProvider` 는 `config/networks.json` 의 공용 Proof Server URL 을 읽는다. 정적 빌드를 Firebase Hosting 또는 Vercel 에 배포 |
| `cli` | 배포, 발급자 등록, Preprod E2E 스크립트 | Node, Wallet SDK 헤드리스 지갑 |

브라우저 private state 는 Midnight.js 의 `privateStateProvider` (IndexedDB) 를 쓴다. 크리덴셜 JSON 은 여기에만 저장되고 서버로 가지 않는다.

### 5.7 하드코딩·폴백 금지 적용 지점

- 네트워크 엔드포인트·컨트랙트 주소·Proof Server URL 은 `config/networks.json` + `.env` 에서만 읽는다. 값이 없으면 **즉시 실패**시키고 기본값으로 덮지 않는다.
- 스키마·연산자·상수는 §5.3·§5.4 의 단일 출처에서만 온다.
- 크리덴셜에 없는 슬롯을 정책이 가리키면 UI 가 요청 생성 단계에서 거부한다. 회로에서 0 으로 대체하지 않는다.
