# 위협 모델 (JobProof on StateProof v2)

> 2026-09-30 · 범위: 컨트랙트 v2, 발급 절차, 지원자·회사·발급자 앱, 제안 파일럿
> 표기: **막음**(회로나 테스트로 확인), **완화**(운영·앱 수준), **남음**(현재 해결책 없음, 이유와 계획을 함께 적음)

## 1. 보호 대상

| 자산 | 누구의 것 | 왜 중요한가 |
|---|---|---|
| 연봉 원값, 공제 내역 | 지원자 | 처우 협상력. 원천징수영수증에는 부양가족 주민번호, 의료비·기부금 칸도 함께 있다([근거](research/2026-09-30-documents.md)) |
| 생년월일, 거주 시·도, 학적 | 지원자(청년) | 채용과 무관한 신상 정보 |
| 지원 이력(어느 회사에 지원했나) | 지원자 | 현 직장에 알려지면 불이익 |
| 판정의 진실성 | 회사 | 위조, 대리 응답을 걸러야 한다 |
| 발급자 서명키 | 발급자 | 유출되면 모든 판정이 무너진다 |

## 2. 공격자와 대응

| 공격자 | 공격 | 결과 | 근거 |
|---|---|---|---|
| 위조 지원자 | 연봉을 고친 증명서 제출 | **막음**: 서명 불일치로 회로가 거절한다 | `refuses claims altered after signing (forged salary)` |
| 위조 지원자 | 남의 증명서를 복사해 사용 | **막음**: 홀더 비밀값 커밋 불일치 | `stolen credential` |
| 위조 지원자 | 가짜 발급자 키로 직접 서명 | **막음**: 발급자 집합 밖이라 거절 | AC-5 |
| 대리 응답자 | 조건 되는 지인이 링크로 대신 증명 | **막음**(봉인 요청): 주체 불일치 / **남음**(공개 공고): 공개 공고는 봉인이 없으므로, 채용 절차에서 봉인 요청으로 재확인해야 한다 | AC-3 |
| 중복 지원자 | 같은 공고에 여러 번 응답 | **막음**: 가명 중복 | AC-1 |
| 과잉 질문 회사 | "연봉 = 5,210만원?", 연봉 공개 요청 | **막음**: 요청 생성 거절 | AC-8 |
| 과잉 질문 회사 | 요청을 나눠 이분 탐색(연봉) | **막음**: 격자 500만원. 몇 번을 물어도 한 칸이 남는다 | AC-11 |
| 과잉 질문 회사 | 요청을 나눠 이분 탐색(생년월일) | **남음**: 격자가 하루 단위라 생일을 좁힐 수 있다. **완화**: 지원자 앱이 같은 회사 링크의 응답 이력을 모아, 합쳐서 폭이 1년 미만이 되는 응답을 경고하거나 막는다. 계획: 생년월일 대신 발급 시점 "만 나이 구간" 칸을 두는 스키마 v3 | ADR §5 |
| 관찰자(체인) | 원장과 트랜잭션에서 값 추출 | **막음**: 누출 스캔 0건(대조군 포함) | AC-12 |
| 관찰자(체인) | 가명으로 공고 간 동일인 추적 | **막음**: 가명이 요청마다 다르다 | AC-2 |
| 관찰자(체인) | 봉인값에 이름 대입 | **막음**: nonce가 링크에만 있다 | AC-3 |
| 관찰자(체인) | 수수료 트랜잭션의 지갑 주소로 추적 | **남음**: 지원자가 자기 지갑(Lace)으로 수수료를 내면, 그 지갑과 응답 트랜잭션이 이어진다. 계획: 수수료 대납(relayer). 대납자가 크리덴셜 값을 받지 않는 구조로 한다 | 로드맵 |
| 관찰자(체인) | 응답 시각과 익명 집합 크기로 추정 | **남음**: 응답 시각과 공고별 응답 수는 공개다 | 공개 설계 |
| 악의적 발급자 | 사실과 다른 값 서명 | **남음**: 발급자 신뢰가 전제다. **완화**: 발급자 집합은 관리자가 등록하고, 공개 레지스트리에 이름이 남는다 | ADR §3 |
| 악의적 발급자 | 홀더 비밀값을 몰래 만들어 연결 | **막음**: 발급 경로가 커밋만 받는다 | AC-4 |
| 발급자 키 유출 | 임의 증명서 발급 | **완화**: 관리자가 `deactivateIssuer`로 즉시 집합에서 뺀다 | AC-5 |
| 관리자 비밀 유출 | 가짜 발급자 등록, 규칙 변경 | **남음**: 관리자 1인 신뢰. 스키마 규칙은 한 번 등록하면 바꿀 수 없다(재등록 거절). 계획: 다중 서명 관리 | 로드맵 |
| 퇴사자 | 재직 중 증명서 재사용 | **막음**: 발급자 epoch 회전 | AC-6 |

## 3. 파일럿 시나리오 점검

1위 JustEnough는 "발급기관 = 운영기관"인 파일럿에서 익명성이 무효가 되는 구멍을 놓쳤다. 같은 유형을 찾기 위해 우리 파일럿을 그대로 대입했다.

**제안 파일럿**: 채용 플랫폼의 경력직 공고 일부. 발급은 브리지 발급자가 맡는다. 지원자가 원본 서류로 한 번 확인받으면 크리덴셜을 발급하고 원본은 폐기한다.

| 질문 | 답 |
|---|---|
| 브리지 발급자가 원본을 보관하면? | 발급 시점 값이 브리지에 남는다. 요구사항은 "확인 후 즉시 폐기"이고, 폐기 여부는 운영 감사 대상이다. 회로로는 강제할 수 없다 → **남음(운영 통제)** |
| 발급자와 채용 플랫폼이 같은 회사면? | 발급자는 subjectId와 holderCommit을 안다. 가명은 `hash(requestId, holderSecret)`이고 비밀값은 지원자 기기에만 있다. 그래서 발급자라도 가명과 사람을 연결할 수 없다. 다만 봉인 요청은 회사가 원래 신원을 아는 경우다 → **막음(가명 연결), 해당 없음(봉인)** |
| 플랫폼이 relayer를 운영하면? | relayer는 증명된 트랜잭션만 받는다. 크리덴셜 값은 받지 않는다. 다만 IP와 시각을 볼 수 있다 → **남음(메타데이터)**. relayer는 아직 구현하지 않았다 |
| 회사가 여러 공고로 같은 지원자를 좁히면? | 공개 공고는 가명이 달라 같은 사람인지 모른다. 봉인 요청은 연봉 격자로 막고, 생년월일은 위 "남음"과 같다 |
| 18세 미만 알바 지원자는? | 근로기준법상 사업장은 가족관계기록사항 증명서를 갖춰야 한다([근거](research/2026-09-30-legal-basis.md)). JobProof는 이를 대체하지 않는다. 청년 스키마는 18세 이상, 지원 단계 확인용으로 한정한다 |

## 4. 데모의 한계

- 데모 인물과 데모 발급자의 비밀값은 누구나 재현할 수 있도록 공개한다(`demoOnly`). 데모 결과는 특정 사람이 아니라 메커니즘을 보여 준다.
- 데모 모드는 브라우저 안의 시뮬레이션 체인에 기록한다. 영지식 증명은 실제로 생성하지만, 공개 네트워크 기록은 아니다. 공개 네트워크 기록은 [devnet 실행 기록](devnet-run.json)과 Preprod 배포(런북 참고)로 따로 남긴다.
